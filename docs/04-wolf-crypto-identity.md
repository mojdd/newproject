# 🪨 وحش ٤ — التشفير والهوية والأمان (Crypto / Identity / Security)

## المشكلة

رسالتك تمرّ بتلفونات **غرباء**. كيف تمنعهم يقرونها؟ وكيف يتأكد المستلم/السيرفر إن
الرزمة منك مو من منتحل؟

اختبار النجاح: **relay ما يقدر يقرأ محتوى unicast؛ والتوقيع يُتحقَّق صح (وتزوير
التوقيع يُرفَض).**

---

## ١. الهوية (Identity)

كل عقدة تولّد محلياً، أول تشغيل، **زوجين مفاتيح**:

| الزوج | الخوارزمية | الغرض |
|-------|------------|-------|
| توقيع | **Ed25519** | يثبت أصل الرزمة (من المرسل فعلاً) |
| تشفير | **X25519** | تبادل مفاتيح / sealed boxes |

- يُولَّدان على التلفون. **المفتاح الخاص لا يطلع أبداً** خارج الجهاز.
- `NodeId` = اشتقاق من المفتاح العام للتوقيع (مثلاً أول N بايت من هاشه) — معرّف
  العقدة بالشبكة.

## ٢. تخزين المفاتيح الخاصة (قيد مهم — انتبه)

> **Android Keystore لا يدعم Ed25519/X25519 مباشرة بشكل جيد.** لا تحاول تولّدهم
> داخل الـ Keystore.

**الحل المعتمد:**
1. استعمل Keystore لتوليد/حفظ **مفتاح AES رئيسي** مدعوم بالعتاد (TEE/StrongBox)،
   `master_wrap_key`.
2. ولّد مفاتيح libsodium (Ed25519/X25519) ببرمجية libsodium.
3. شفّر المفاتيح الخاصة بالـ AES الرئيسي، واخزن الـ ciphertext بقاعدة
   **SQLCipher** ([وحش ٧](07-wolf-storage.md)).
4. عند الحاجة، فُكّ تشفيرها بالـ Keystore key بالذاكرة فقط، وامسحها بعد الاستعمال.

هذا القيد لازم **يُوثَّق ويُنفَّذ صح** — مو يُتجاهل.

## ٣. التشفير E2E عبر sealed boxes

- استعمل **`crypto_box_seal`** (sealed box): يشفّر لمفتاح عام **بلا handshake
  تفاعلي**.
- **ليش sealed box مثالي للـ mesh:** ما تكدر تسوي جلسة (session/handshake) مع عقدة
  متحركة قد تختفي بأي لحظة. sealed box يخلّيك تشفّر للمستلم بمجرد ما تعرف مفتاحه
  العام، بلا أي تفاعل مسبق.
- آلية كل رزمة شخصية (unicast):
  1. **شفّر** الحمولة لمفتاح **المستلم** العام (`crypto_box_seal`).
  2. **وقّع** الرزمة (الـ header + الحمولة المشفّرة) بمفتاح **المرسل** الخاص
     (Ed25519).
  3. الوسطاء يمرّرون **blob مشفّر + توقيع** — ما يقدرون يفكّونه (ماعندهم المفتاح
     الخاص للمستلم).

> ملاحظة خصوصية: sealed box يخفي **هوية المرسل** عن غير المستلم بحد ذاته؛ لكن لأننا
> نوقّع بـ Ed25519 لإثبات الأصل، هوية المرسل تكون ظاهرة بالـ header. هذا مقصود
> (نحتاج إثبات أصل للإيصالات وضد الانتحال). الموثوقون فقط يربطون الـ NodeId باسم.

## ٤. أمان السيرفر (البوابة)

- **مفتاح السيرفر الحكومي العام مثبّت (pinned)** ومدمج بالتطبيق → البوابة تتأكد
  إنها ترفع للسيرفر الصح مو منتحل.
- **TLS certificate pinning** عند الرفع عبر HTTPS (طبقة ثانية فوق الـ pinning
  المنطقي).
- الرفع **موقّع** بمفتاح العقدة عشان السيرفر يتحقق من الأصل ([وحش ٥](05-wolf-gateway.md)).

## ٥. طبقتا الثقة (Trust Tiers)

| الطبقة | يشوف | كيف يُضاف |
|--------|------|-----------|
| **موثوق (Trusted)** | اسمك وموقعك (عنده مفتاحك العام مربوط باسم) | **QR وجهاً لوجه** |
| **غريب (Stranger)** | لا شي — يمرّر blob فقط | تلقائي (relay مجهول) |

- إضافة موثوق عبر **QR** = تبادل **out-of-band** للمفاتيح العامة → يمنع
  **MITM** (ماكو طرف ثالث بالوسط وقت التبادل).
- الـ QR يحمل: المفتاح العام للتوقيع + المفتاح العام للتشفير + اسم ظاهر اختياري.

## ٦. واجهة مقترحة (pure Kotlin — قابلة لاختبار JVM عبر lazysodium-java)

```kotlin
interface CryptoEngine {
    fun generateIdentity(): Identity                       // Ed25519 + X25519
    fun seal(plaintext: ByteArray, recipientPub: PublicKey): ByteArray   // crypto_box_seal
    fun unseal(ciphertext: ByteArray, me: Identity): ByteArray?
    fun sign(message: ByteArray, me: Identity): Signature  // Ed25519
    fun verify(message: ByteArray, sig: Signature, senderPub: PublicKey): Boolean
}

interface KeyVault {                 // Android-only (Keystore + SQLCipher)
    fun storeEncrypted(id: Identity)
    fun load(): Identity?
}
```

> `CryptoEngine` **منطق نقي قابل لاختبار JVM** عبر `lazysodium-java` (Maven
> Central). `KeyVault` (Keystore wrapping) أندرويد فقط.

## ٧. حالات اختبار (وحدات — JVM)

- [ ] `unseal(seal(m, recvPub), recv) == m`.
- [ ] عقدة ثالثة ما تكدر تفكّ sealed box (ماعندها المفتاح الخاص) → `null`/فشل.
- [ ] `verify(m, sign(m, A), A.pub) == true`.
- [ ] تعديل بايت واحد بالرسالة أو التوقيع → `verify == false`.
- [ ] توقيع من B يُتحقَّق ضد A.pub → `false`.
