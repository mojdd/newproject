# 🪨 وحش ٥ — البوابة الانتهازية → السيرفر الحكومي (Opportunistic Gateway)

## المشكلة

لمن عدة عقد تلمس نت بنفس الوقت، لو كلها ترفع نفس الداتة → **تكرار وحرق بطاريات**.

اختبار النجاح: **عقدة واحدة (الأقوى) ترفع، الباقي يسكت، والسيرفر يستبعد أي تكرار
متبقّي عبر Message IDs.**

---

## ١. انتخاب البوابة (Gateway Election)

- العقدة اللي تلمس نت **تعلن** قدرتها بالـ mesh (gossip خفيف): «أنا أكدر أرفع».
- بين العقد القريبة اللي عدها نت، تُختار **الأقوى** للرفع:
  - **مستوى البطارية** (الأعلى يفضّل).
  - **قوة الإشارة/جودة النت**.
  - كاسر تعادل: أعلى `NodeId` (deterministic).
- الباقي **يسكت** — يعطي البوابة المنتخبة فترة، ولو ما رفعت (اختفت) يعيد الانتخاب.
- الآلية **gossip لا-مركزية** — ماكو منسّق مركزي.

## ٢. حماية إضافية: رفع Idempotent

حتى لو فشل الانتخاب وارتفعت داتة مكررة، السيرفر **يستبعد التكرار** عبر
**Message IDs**:

- كل رزمة/سجل له `MessageId` فريد ([وحش ٢](02-wolf-routing.md)).
- إعادة الرفع **آمنة** (idempotent) — السيرفر يتجاهل ما رآه سابقاً.
- يعني الانتخاب **تحسين** (يقلّل الهدر)، مو شرط صحة — الصحة مضمونة بالـ idempotency.

## ٣. ماذا يُرفع — جدول ملزم ⚠️

| النوع | يُرفع؟ | كيف |
|-------|--------|-----|
| بيانات تجميعية (عدد، كثافة، وجبات، مخزون، تواليتات، ماء، إسعاف، صحة عامة، حركة مواكب) | ✅ | **مكشوفة** للسيرفر |
| شفافية المواكب (دعم، صرف، موردين، طاقة) | ✅ | مكشوفة — شفافية كيان خدمي |
| رسائل ومواقع الأفراد | 🔒 | **مشفّرة E2E تمرّ عبوراً فقط** — السيرفر يخزّنها/يمرّرها كـ blobs، ما يقراها |
| أي بيانات فردية بالاسم | ⛔ | **لا تُجمع أصلاً** — انظر [الخطوط الحمراء](10-red-lines.md) |

> السيرفر **وجهة تجميعية + ساعي بريد للـ blobs المشفّرة** — لا أكثر. ما يقرأ
> محتوى الأفراد، وما يجمع بيانات فردية بالاسم إطلاقاً.

## ٤. البروتوكول

- **رفع دفعي (batch)** — يجمع المخزون التجميعي + blobs الشخصية ويرفعهم دفعة.
- **موقّع** بمفتاح العقدة (Ed25519) → السيرفر يتحقق من الأصل.
- **idempotent** — مفاتيح الـ MessageId تمنع التكرار.
- **server pinning** ([وحش ٤](04-wolf-crypto-identity.md)) + **TLS cert pinning**
  → ضد سيرفر منتحل و MITM.
- السيرفر يردّ **ACKs** بالـ MessageIds المستلمة → تتحوّل رزم
  [وحش ٣](03-wolf-store-and-forward.md) لـ `UPLOADED_SERVER` ثم `ACKED`،
  والإيصالات **تفيض رجوعاً** بالـ mesh.

## ٥. واجهة مقترحة

```kotlin
interface GatewayManager {
    fun onInternetAvailable()                  // يبدأ الإعلان عن القدرة
    fun onInternetLost()
    val isElectedGateway: StateFlow<Boolean>   // نتيجة الـ gossip election
}

interface ServerUploader {                     // يُستدعى فقط لو منتخب
    suspend fun uploadBatch(batch: UploadBatch): UploadResult   // موقّع + pinned
}

data class UploadBatch(
    val aggregates: List<AggregateRecord>,     // مكشوفة
    val opaqueBlobs: List<EncryptedPacket>,    // عبور E2E فقط
)
```

> **منطق الانتخاب** (مقارنة score، gossip، إعادة الانتخاب) **قابل لاختبار JVM**.
> الرفع الفعلي (HTTPS + pinning) يحتاج شبكة/بيئة أندرويد.

## ٦. حالات اختبار

- [ ] بين ٣ عقد عدها نت، الأعلى score يصير `isElectedGateway=true` والباقي
      `false`.
- [ ] لو البوابة المنتخبة اختفت، يُعاد الانتخاب لثاني أقوى.
- [ ] رفع نفس الـ batch مرتين → السيرفر يستبعد التكرار (idempotent) — لا سجلات
      مكررة.
- [ ] أي بيانات فردية بالاسم **غير موجودة** بالـ `UploadBatch` (تحقّق ضد
      [الخطوط الحمراء](10-red-lines.md)).
